# ADR 0007 — Nulavio AI Bridge: MCP for external agents, one policy decision point, an AI Workspace per agent

- **Status:** Accepted (2026-10-26). **Foundation implemented (S4)**: `nulavio ai`, MCP server, AI Workspace, Policy Decision Point, audit; tested with real Claude Code. **Autonomy and its UI implemented (S7)**: Settings → AI & Automation, permission requests in the browser, pause, new keys, client evidence, activity retention, adapter hardening (dialogs, downloads, uploads). **Profiles, routing and the connect wizard implemented (S8).** **Built-in assistant (A12) and raw automation (A13) implemented (S20).** **Amended 2026-10-28 (UX1, D-UX4):** raw automation is no longer part of Full control; it is a separate opt-in per agent ([amendment](#amendment-2026-10-28-raw-automation-leaves-full-control-ux1-d-ux4)).
- **Related:** [brief](../product/briefs/2026-10-26-ai-bridge.md), [architecture](../architecture/ai-bridge.md), [threat model for automation](../security/threat-model-ai.md), [compatibility matrix](../ai/compatibility.md), [ADR 0003](0003-nulavio-profiles-and-routing.md) (profiles), [ADR 0006](0006-nulavio-vault.md) (Vault).

## Context

Users want AI agents (Claude Code, Codex, others) to use the browser, with autonomy ranging from "read only" to "full control". The engine already has a standard automation protocol (WebDriver BiDi). An agent that speaks it directly is the most capable option, but it is also all-or-nothing: whoever holds a BiDi connection controls the whole browser, every profile it has open, and can disable protections. Nulavio needs a layer that agents can use without setup friction, that applies the user's choices on every call, and that never trades the user's protections for convenience.

Audit (A0), 2026-10-26:
- Engine: Gecko 158.0.1 (Nulavio build, Track B) and distribution Firefox 158.0.1 (Track A). Both ship the Remote Agent with WebDriver BiDi; CDP was removed from Firefox in 141.
- No automation code existed outside the tests (Marionette client in `tests/lib/marionette.py`). The launcher refuses `--marionette`, `--remote-debugging-port` and similar flags for normal profiles (`engine.FORBIDDEN_FLAGS`).
- The Remote Agent applies "recommended preferences" by default. In 158 these **turn off Safe Browsing (phishing, malware, downloads), app and extension updates and the pop-up blocker**, among others (`remote/shared/RecommendedPreferences.sys.mjs`). They suit test farms, not a browser that visits the real web.
- Clients present: Claude Code 2.1.308, Codex CLI 0.164.0. Neither Claude Desktop nor Codex Desktop is installed.
- MCP: the latest specification is 2026-07-28 (stateless; `server/discover`; per-request `_meta`). Clients in the field still use the 2025 `initialize` handshake.

## Options

| Option | For | Against |
|---|---|---|
| A. Agents speak WebDriver BiDi (or Marionette) directly | Maximum capability; existing tools (Puppeteer, Selenium, firefox-devtools-mcp) | No per-agent policy: a connection controls everything; port open to every local process; recommended prefs weaken protections unless the tool turns them off |
| B. Point agents at Mozilla's firefox-devtools-mcp | Maintained by Mozilla; many tools | Node.js dependency; its own launch and prefs; no Nulavio policy, audit or profile model |
| C. **Nulavio MCP server (stdio) + Policy Decision Point + AI Workspace, driving the engine over BiDi** | One place for grants, audit, revocation and stop; works with any MCP client; no change to the engine | Fewer tools than raw BiDi at first; the bridge must keep up with the protocol |
| D. Engine patch with a built-in agent API | Fine-grained control inside the engine | Large patch surface on every engine update; not needed for the first slices |

## Decision

1. **C now, A as an explicit "raw automation" option later.** The MCP server is the default path. Raw BiDi for advanced users (A13/Full control) will be a separate, explicitly enabled mode that says plainly that the protocol bypasses the bridge's per-call policy.
2. **Transport: MCP over stdio, started by the agent** (`nulavio ai serve`). No network listener for agents; the only listener is the engine's BiDi endpoint on `127.0.0.1` with a random port, which the engine protects against web pages (it rejects WebSocket upgrades that carry an `Origin` header or a foreign `Host`). The server is **dual-era**: it answers `initialize` (2025-03-26, 2025-06-18, 2025-11-25) and modern 2026-07-28 requests with `_meta` and `server/discover`. Standard library only (decision D6): no SDK dependency, tested against real clients.
3. **Agent identity: a token per registered agent**, generated by `nulavio ai add`, shown once, stored only as SHA-256. It identifies the *configuration* that launched the server, not the program; any same-user process that reads the agent's config can present it (documented, threat model AI-T7). Unknown or revoked tokens: the server refuses to start.
4. **Policy Decision Point outside the model** (`ai/registry.decide`). Order: emergency stop → revocation → site list → explicit grant (allow/ask/block; forever, for N minutes, or for one bridge session) → autonomy preset. "Ask" goes to a desktop dialog outside the browser the agent controls (KDE `kdialog`); with no way to ask, it fails closed. No MCP tool reads or changes policy; the policy file is re-read on every call, so changes apply to the next call.
5. **Autonomy levels** (presets per capability; the user can override each capability):

   | Capability | Restricted | Assisted | Autonomous | Full control |
   |---|---|---|---|---|
   | read pages, navigate, screenshots | allow | allow | allow | allow |
   | click and type | ask | allow | allow | allow |
   | submit forms | ask | ask | allow | allow |
   | files, signed-in sessions, background work | block | ask | allow | allow |
   | purchases, account settings | block | ask | ask | allow |
   | local network / internal pages, JavaScript, network inspection, other profiles, private tabs | block | block | ask | allow |
   | cookies and storage | block | block | block | allow |
   | raw automation and privileged pages ("debugging"; [amendment of 2026-10-28](#amendment-2026-10-28-raw-automation-leaves-full-control-ux1-d-ux4)) | block | block | block | block: a separate opt-in per agent |

   Purchases, account settings, background work, network inspection and private tabs left this table on 2026-11-25: no tool checked them ([amendment](#amendment-2026-11-25-capabilities-no-tool-checks-are-not-offered-714)). "Other profiles" is `multiple_profiles` (item 9): a second place at once, a profile beside the AI Workspace or two profiles; one profile on the agent's list, alone, needs only `authenticated_sessions`.

   Full control needs an explicit acceptance of a warning (`--accept-full-control`; the Shell screen in S7). "Autonomous" never asks again for what it covers (tested).
6. **AI Workspace: one engine profile per agent**, separate cookies, history, downloads and storage; persistent or disposable. It is the only place where the Remote Agent runs. Its prefs are the Nulavio baseline plus `remote.prefs.recommended=false`, so Safe Browsing, updates and the pop-up blocker stay on (tested with a positive control). Sandboxes are untouched (`engine.launch_env`). `navigator.webdriver` is true there, as the standard requires; sites can tell automation apart.
7. **Addresses are classified before navigation** (`policy.classify_url`): http(s) only by default; the local network, this computer, `file:` and `about:` pages need `local_resources` (and `debugging` for privileged pages); `javascript:`, `data:` and URLs with credentials are refused. Clicks that follow a link or submit a form are checked against those capabilities too.
8. **Audit keeps actions, not content**: agent, session, tool, capabilities checked, decision and reason, target origin, outcome, duration, sizes. Never page text, typed text, scripts or screenshots. Rotates at 2 MB.
9. **Real profiles only when the user gives them** (S8): per agent, a list of the user's profiles and per-agent routes (site → profile). Using one needs `authenticated_sessions`; working in more than one profile at a time (the AI Workspace included) needs `multiple_profiles`. A profile opens for an agent in its own engine instance only while it is closed in the user's windows and never while it is locked: automation permission never implies a key.
10. **Nulavio never edits another program's configuration itself.** It prints the configuration, or (S8) shows the exact command of the agent's own CLI (`claude mcp add-json --scope user …`, `codex mcp add …`) and what it changes, and runs it only after the user's click. Configurations hold no secret: they point to the agent's key file (0600) in Nulavio's state.

## Consequences

- Any MCP client can use the browser with one command and one configuration block; the user's choices apply to every call and can be withdrawn at once (revoke, stop).
- The bridge only governs what goes through it. A CLI agent with shell access runs as the user and can do anything the user can, including editing Nulavio's files or starting its own browser; the bridge does not and cannot prevent that. This is stated in the UI and the threat model.
- Pages can still do what pages do once loaded (redirects, scripts, requests to the local network); the PDP decides what the *agent* asks for. Engine protections (Safe Browsing, ETP Strict, HTTPS-Only, pop-up blocker, sandboxes) remain the defence for page behaviour.
- The tool set is smaller than raw BiDi or firefox-devtools-mcp. It grows per milestone (downloads, uploads, network inspection, profiles), each with its capability.
- The bridge and the built-in assistant are the only AI paths (UX1, decision D-UX7). Mozilla's own AI features would bypass this ADR, so they are off as defaults: the chatbot (`browser.ml.chat.enabled/page/menu/shortcuts`), smart tab groups, Link Preview and its key points, Smart Window (`browser.ai.control.*` = `blocked`, the value Firefox's AI controls write), local models for extensions (`extensions.ml.enabled`) and Nimbus rollouts that could turn them on. Track B sets them in `firefox-branding.js`, Track A seeds the same values from `baseline.js` (a unit test keeps both equal); the person can still turn a feature on in the engine's settings. Verified on the rendered window: `tests/integration/test_mozilla_features.py`.

## Implementation (S4, 2026-10-26)

Package `launcher/nulavio_launcher/ai/`: `mcp.py` (protocol), `tools.py` (11 tools and per-call enforcement), `policy.py` (capabilities, presets, address classification), `registry.py` (agents, grants, stop switch, approvals), `audit.py`, `workspace.py` (engine launch), `bidi.py` and `websocket.py` (protocol client), `cli.py` (`nulavio ai add | agents | grant | autonomy | revoke | remove | stop | resume | audit | capabilities | serve`).

Tests: `tests/unit/test_ai_bridge.py` (40), `tests/integration/test_ai_bridge.py` (13, on the Nulavio build and on distribution Firefox), `tests/integration/test_ai_agents_real.py` (opt-in, real Claude Code and Codex CLI). Results: [compatibility matrix](../ai/compatibility.md).

## Implementation (S7, 2026-10-26): autonomy, permission requests, Settings

- **Settings → AI & Automation** (`browser/shell/settings/ai.js`): connect an agent in three decisions (agent, autonomy, connect; the configuration with its key is shown once and copied by the user), agents with level, last connection and sites; per capability allow / ask / block, for 30 minutes, 8 hours or until changed; pause, revoke, new key, remove; emergency stop; activity (last 30 days, metadata only, clearable). Full control asks for the warning first. The page talks to `nulavio ai api` (JSON on stdin); agents never reach it.
- **Permission requests in the browser.** "Ask" now writes a request file; the user's Nulavio window opens "Agent permission request" (agent, autonomy, what, where; Allow once / for this session / Deny, Deny focused). If no Nulavio window takes it within 4 seconds, the KDE dialog asks; with neither, the answer is no. Windows of an AI Workspace (pref `nulavio.ai.workspace`) never show or answer requests — the agent drives them — and show a bar naming the agent.
- **Pause** holds an agent without revoking it; **new key** replaces the token at once; **client evidence**: the program that started the bridge (its executable name) is recorded and shown, with a warning when it does not look like the registered client (evidence only, never a grant).
- **Adapter hardening.** Page dialogs stay open for the agent (`dialog` tool) and clicks that open one return instead of hanging; downloads follow the `files` capability *in the engine* (`browser.setDownloadBehavior`: allowed into the workspace's downloads folder, else refused) and are listed by `downloads_list`; `upload` takes only files the user placed in the workspace's uploads folder. For agents that may use files, the workspace lets page processes read that one folder and build a File from it (`security.sandbox.content.read_path_whitelist`, `dom.file.createInChild`); the content sandbox stays on and nothing else becomes readable.

## Implementation (S8, 2026-10-26): connect wizard, profiles and routes

- **Key file.** `nulavio ai add` writes the agent's key to `$XDG_STATE_HOME/nulavio/ai/tokens/<agent>.token` (0600); configurations carry `NULAVIO_AGENT_TOKEN_FILE`. A new key replaces the file: the agent's configuration stays valid. Nothing secret appears in `.mcp.json`, `config.toml` or on a command line.
- **Connect wizard** (Settings → AI & Automation and `nulavio ai connect`): detects Claude Code and Codex (path, version), shows the exact command and the file it changes, runs it after approval, then asks the agent's own tool (`mcp get`); Claude Code also starts the server and reports "Connected". Tested with the real CLIs against a throwaway HOME; the user's real settings were hashed before and after.
- **Profiles and routes per agent.** In the agent's permissions: the user's profiles it may use and routes (site → profile, most specific wins). `tab_new` follows routes (or an explicit `profile`), `profiles_list` shows where the agent can work, `tabs_list` says which profile each tab is in. Each profile runs in its own engine instance driven over BiDi; its `user.js` gets four temporary lines (no remote-agent test preferences; "an agent drives this window", tied to the bridge's process; the target kind and the profile's name) removed when the session ends, together with the values the engine saved from them in `prefs.js`, once its engine has exited (#639; a killed bridge leaves both until the next agent session there, R36). Those four names are the Bridge's in a profile it is given: the Guard refuses `remote.prefs.recommended` at any value in a user profile, and `nulavio.ai.*` are Nulavio's own, so an agent session also removes values it did not write, such as one set by hand, when the line is one `user_pref()` of one literal value, as the engine writes `prefs.js` (a `pref()` line, or one that also sets another pref, stays). Refused: profiles not given, open in the user's windows, or locked.
- **Sessions.** "connected" and "disconnected" events; Settings shows agents connected now.

Tests: unit +2 (key files, profiles and routes), engine +2 (routed tab in a given profile, multiple-profiles rule, cookie separation, temporary lines removed; refusals for not given, open and locked profiles), UI +2 (the wizard with real CLIs; the profiles and routes editor).

Tests (S7): `test_ai_bridge` unit +9 (pause, keys, client evidence, browser approvals with fallback and timeout, retention, Settings API) and engine +3 (downloads per permission, dialogs, uploads), `tests/integration/test_ai_ui.py` (6: connect from Settings, full-control warning, request page answering a real bridge request, pause/permissions/stop/revoke, activity, AI Workspace never answering).

## Implementation (S20, 2026-10-27): built-in assistant (A12) and raw automation (A13)

**Nulavio Assistant (A12).** A side panel (sidebar) and a card in Settings → AI & Automation. Provider-agnostic: any endpoint compatible with OpenAI's chat completions (OpenAI, OpenRouter, Mistral, local servers such as Ollama, llama.cpp or LM Studio) or Anthropic's Messages API; no Nulavio account, model or proxy. The API key goes from the settings form, once, through the Nulavio tools into the system keyring; the tools read it when they call the provider, so it never stays in the browser (`launcher/nulavio_launcher/ai/assistant.py`). The key belongs to the API kind and the origin it was saved with: a request goes with it only to that kind and origin, saving another one with the key field empty removes it, and a task whose provider changes in Settings stops before its next model turn (threat model AI-T40). Each profile decides whether it may send anything to the model; the page's visible text (the engine's own `PageExtractor`, no script in the page) goes along only when the user ticks "include this page", with the page's title and its address reduced to origin and path (never its user part, `?query` or `#fragment`, #653), and the panel names the recipient, that address and how many characters left. Answers are shown as plain text. Tasks: the assistant is an agent in the same registry ("Nulavio Assistant", Restricted when created); its tool calls are `Bridge.call`, so the same Policy Decision Point, audit, pause, revoke and emergency stop apply, in its own AI Workspace. Verified: `test_assistant` (unit: endpoints, keyring only, consent per profile, page only when given, both APIs, tasks under the policy, stop) and `test_assistant_ui` (real engine: key in the keyring and in no profile file, page text through the engine's extractor only when included, panel renders text, a task's local address refused under Restricted).

**Raw automation (A13).** The `raw_automation` tool hands the AI Workspace's WebDriver BiDi endpoint to the agent's own library (Puppeteer and Selenium speak BiDi to Firefox; Playwright needs its patched Firefox and CDP was removed from Firefox). It needs the "Privileged debugging" capability (blocked in every preset but Full control; since the [amendment of 2026-10-28](#amendment-2026-10-28-raw-automation-leaves-full-control-ux1-d-ux4) blocked in every preset, Full control included, and turned on only by its own per-agent opt-in). The bridge ends its own BiDi session so the agent can start one, turns its other tools off for that workspace, and says plainly that nothing done through the endpoint is checked, asked about or logged. The user's stop, pause and revoke still end the workspace: a watcher in the bridge checks the registry every second, and closing the bridge ends it too (`raw-ended` in the activity log). Never offered for the user's own profiles. Verified: `test_ai_bridge` 20 (denied without the capability; a separate BiDi client opens a session and navigates; the emergency stop ends the engine).

## Implementation (UX1, 2026-10-28): the assistant's consent, private windows and stop

Fixes from the [UX audit](../design/audit-2026-10-27.md) (AI-01, AI-02, AI-15, AI-10, part of AI-04 and AI-12), under decisions D-UX5 and D-UX6. Each one only tightens what the assistant may send.

- **The side panel finds its page (AI-01).** Gecko 158 renamed `Node.ownerGlobal` to `documentGlobal`. The experiment read the old name through optional chaining, so the panel in the sidebar never found its window: "Incluir esta página" and "Resumir esta página" were always unavailable. It now reads `documentGlobal` and falls back to `ownerGlobal` for older engines. The tests drive the real sidebar, through a frame script in the panel's browser, instead of opening the panel as a tab.
- **Consent per message, bound to one tab (AI-02).**
  - "Incluir esta página" captures `{tabId, url, title}` at the click. The panel shows an item, "Texto, título e endereço da página · só da aba “title” · address", with a remove control and the recipient. The address is the one that goes with the text: origin and path, without the user part, query or fragment (#653; until then the item named the host and the whole address went).
  - The item leaves the message after every Send, whatever goes: a question, a Task or "Tentar de novo", which take none, or a start that is refused. "Resumir" only includes the page and writes the question: what was already included stays until that Send. The browser drops its copy of the text then too, so it never comes back in a later message (#678; until then a Task or a retry left it there, and the panel showed it again when it reopened). An item the panel shows also leaves when another tab is selected, or when that tab goes to another address or closes. The panel then says why ("“title” era de outra aba e saiu da mensagem" or "… não está mais nesta aba …") and only *offers* the new page. The panel reads the selected tab again on each tab event; a Send pressed while that check is on its way waits for it, and for a newer one, and then takes only the items the tab selected then still holds. A check that a mode change or a removal made void meanwhile is read again first, and nothing goes if the panel went to another state (a pause) meanwhile (#816; until then a Send pressed before the check came back carried the item of the tab just left). A trip to another tab and back before the check comes back keeps the item, since the later check reads the first tab again: it is still bound to the tab selected then.
  - Nothing leaves without first being shown in the panel. An item the panel has not drawn yet when another tab is selected (the panel was closed, or its opening reads were still on their way) is checked against the tab selected when the panel next draws it, and cannot be sent before then. So a trip to another tab and back before that draw does not end it: the item is drawn, with its tab and its remove control, and goes with the next Send unless the person removes it. The browser does not drop the window's items on a tab change by itself (rule settled on #790, 2026-11-26).
  - A pending Include or Summarise reply belongs to that context revision. Send, a mode change or a page refresh invalidates it, so a late reply cannot reattach the page to the next message or send another request. The browser holds to the same rule on its side: an Include still reading when a message starts, even one that is refused, keeps nothing, even when the panel closed meanwhile (#678). The list of items the panel reads from the browser, when it opens or an entry point delivers one, follows the same rule: a reply read before a Send and received after it is discarded and the list read again, so it cannot show an item that Send took (#739). The browser takes the items at a start before it awaits anything, even the check of an `agent:pid` window, so a list read meanwhile is already empty. The panel draws the list it read before any other await, so Send carries only items it shows. When it opens, and when an entry point delivers an item, it reads that list together with the selected tab and drops what that tab does not hold before drawing it, with no await in between, so an item kept for another tab never goes with a Send; a delivery while the panel opens waits for that check, and the panel says why an item left (#758, #773). Those reads start no new context revision, so an Include, or a tab event's check, still on its way when the panel renders again goes on: the check drops what its tab does not hold as soon as it arrives. A list the panel read is drawn only when nothing changed its items while that read was on its way: a Send, an item included, removed or dropped (an Include cancelled meanwhile too), a tab event, or an entry point's delivery that added or replaced an item means it is read again; the shortcut and “@ia”, which change no item, do not, nor does a read that finds the items and the tab as the panel already draws them. So a reply never brings back an item that left or was replaced, never removes one an Include just drew, and an item that leaves is dropped and announced once (#759). When it renders again after a refusal, the line above Send names the recipient Send would use before anything is read. When it opens, it draws neither that line nor the “no page” hint until it has read the conversation and the selected tab. When it shows its composer again after another state (a pause, the setup page), the line, the items, the offer to include the page and that hint drawn before stay hidden until those reads.
  - `assistantAsk(question, {tabId, url})` resolves that tab through the engine's WebExtension tab ids. The tab must be in the calling window and at exactly that address. A `#fragment` change counts, because apps that route by fragment show other content. The module checks again after extraction. Otherwise it refuses with `page-changed`, and nothing is sent. The tab selected at Send time is never read.
- **Never in private windows (AI-15, D-UX6).** The module refuses page, ask and task when the calling window is private (`private-window`). A private tab named from a normal window is refused as `page-changed`. In a private window the panel shows "Desligado nesta janela privativa" instead of the composer.
- **Stop, pause and revoke cover questions too (AI-10, D-UX5).**
  - `nulavio ai assistant` refuses `ask` and `task` before anything is sent while any of these holds: the emergency stop is on (`emergency-stop`), or the assistant's agent is paused (`assistant-paused`), revoked or removed (`assistant-revoked`). `state` reports the reason as `blocked`.
  - A task checks the registry again before every later model turn. When the stop, a pause or a revocation arrives mid-run, the task ends with `stopped: <reason>` and makes no further provider call.
  - The panel shows "Parada de emergência ativa", "Assistente pausado" or "Assistente revogado", with a button to Settings to resume. The emergency stop's hint in Settings now says it covers the assistant.
  - Saving the assistant's settings after a revocation creates a new Restricted agent; the revoked record stays for the audit. This makes the existing "save again to create another" message true.
- **Honest task endings (AI-04, today's part).**
  - Progress carries no ✓ (status level `progress`, shared with the other Shell pages).
  - The step limit reads "Parou após 8 passos sem concluir" (`limit` in the result).
  - Sometimes the tools end without an answer: the 10-minute limit kills them, or they crash. The module then answers `task-unfinished`, and the panel says that actions may have happened in the Área de IA, with a button to Atividade. It never says "Nada foi alterado" after a task has started.
  - Permission request pages open with `inBackground: false`. In Firefox 158 and 159, `openTrustedLinkIn` already defaults `forceForeground` to true, so the background tab the audit inferred does not happen there. The explicit option pins the behaviour against later engine changes, and a test guards it.
- **Accessibility basics (AI-12).**
  - One polite announcement when a message is sent ("Enviado para …") and one at the end ("Resposta pronta.", or the reason it stopped).
  - The answer region is not live; it sits under an `h2` "Resposta". A receipt says what went ("N caracteres do texto desta página, com o título e o endereço…" or "Só a pergunta…").
  - Ctrl+Enter sends (`aria-keyshortcuts`). A quick action that is unavailable is hidden, and the panel says why.

Verified on the Firefox 159 Track B build: `test_assistant` unit, 11 tests. New tests cover the stop, pause and revoke blocking questions, page text and tasks, a stop mid-run without a second model turn, the step limit, and a new agent after a revocation. `test_assistant_ui` integration, 12 tests (including delayed Include and Summarise replies). They cover the real sidebar offering the page title; the item's binding, removal and clearing after Send and Summarise; the drift message on a tab switch and on navigation; `page-changed` for another address, another `#fragment` or a closed tab; nothing from private windows; the stop and pause in the panel; the step-limit and killed-tools endings; and the request tab in front. Against the previous Shell and tools, 9 of these fail and 2 error; the request-tab test passes there too, for the reason above.

## Amendment 2026-10-28: raw automation leaves Full control (UX1, D-UX4)

**Change.** The `full_control` preset now allows every capability except `debugging` (policy.`RAW_CAPABILITY`), which covers the `raw_automation` tool and privileged pages (`about:`, `chrome:`, `resource:`). No level includes it. It is a separate per-agent opt-in, "Automação bruta" in Settings → IA e automação (a switch in the agent's permissions, not in the capability list), with its own critical confirmation. The registry records it as `raw_automation_accepted` (a timestamp). `policy.effective_mode` returns `block` (`raw-automation-off`) for `debugging` while that field is empty, whatever the grants say. `registry.grant` refuses `allow`/`ask` for it without `accept_raw_automation` (code `raw-automation-not-accepted`); `block` or clearing it turns the opt-in off, so turning it on again shows the warning again. CLI: `nulavio ai grant <agent> debugging allow --accept-raw-automation` (the CLI prints `policy.RAW_AUTOMATION_WARNING`).

**Changelog: this only tightens.** Existing registries lose raw automation until the user opts in. This covers agents at Full control that relied on the preset, and agents with an explicit `debugging` grant made before this amendment, because that grant was given without the raw-automation warning. Under Full control, privileged pages (`about:config`) now also need the opt-in. Nothing that was blocked becomes allowed.

**Consent in the user's language (SPA-01, SB-02, SB-03).** The browser no longer shows the tools' English `FULL_CONTROL_WARNING`. That constant stays for the CLI only. The Settings API (`nulavio ai api`) returns no consent text, only error codes (`full-control-not-accepted`, `raw-automation-not-accepted`, from `RegistryError.code`). The Shell renders its own locale keys: `aiFullControlBody` says concretely what turns on (every action without asking, purchases and payments, account changes, private tabs, the profiles in the agent's list, running scripts) and that raw automation is *not* included; `aiRawBody` says that nothing done through the endpoint is checked, asked about or recorded. Both use the critical variant of the confirmation dialog (critical icon, the agent's name in the title, primary-colour body, `alertdialog`, Cancel focused first).

**Permission requests (SB-01).** The request file carries the capability's risk tier (`policy.RISK`: critical for money, code, the user's data and places outside the AI Workspace; warning for what changes pages or sends data; info for reading) and the place the call acts in (`{"kind": "workspace"}` or `{"kind": "profile", "profile": <label>}`; `registry.decide(place=…)`, also in the desktop dialog). `ai/request.html` shows the agent and its level, the request, a risk callout (icon + words + level colour), the address, where the agent acts, and the expiry as a clock time ("Sem resposta até 14:32, o pedido é negado"). **Deny is the filled primary, first and focused**; "Permitir uma vez" is secondary; "Permitir até o agente desconectar" (until now "nesta sessão") is quiet. "Gerenciar agentes" opens in a new tab.

**Window states (WCS-01, WCS-02, AI-06).** A window an agent drives shows a bar the user cannot close (`appendNotification(…, dismissable = false)`). The bar names the agent and its level, says where it acts, and has "Parar agente", which pauses that agent: clicking it can only stop the agent, so it is safe in the window the agent drives, and resuming stays in the user's own Settings. The launcher writes `nulavio.ai.target` = `workspace` into an AI Workspace. For one of the user's profiles it writes `profile` plus `nulavio.ai.target.label`, as temporary lines (removed with their saved copies in `prefs.js` when the session ends, #639); the bar then says "<agente> está usando o seu perfil <nome>", at warning priority.

When `raw_automation` hands the endpoint over, the bridge writes `nulavio-raw.json` (`{"agent", "pid", "since"}`, 0600) into the AI Workspace's profile. It is removed when the workspace starts or stops. The Shell polls it each second. Once it sees the file for its own agent, from a live bridge, it latches the window into raw mode until the window closes, so deleting the file does not undo it. It replaces the bar with a critical one that cannot be closed: "Automação bruta: o Nulavio não verifica nem registra o que acontece nesta janela", with "Parar agente". The root element's `nulavio-state` attribute carries `ai`, `ai-profile` and `raw` for the window theme (UX3). The marker is a cue for the window, not a control: the bridge's own state and its watcher still end the workspace on stop, pause or revoke.

## Amendment 2026-11-03: approvals only tighten (UX5-0)

**Change.**
- **The answer is checked again.** A permission prompt can stay open for minutes. `registry.decide` now checks the emergency stop, pause, revocation, the site list and a block the user set meanwhile again after "once" or "session". If any of them now refuses, the call is refused with that reason (`stopped`, `paused`, `revoked`, `out-of-scope`, `grant`).
- **Pending requests end early.** `BrowserApprover` denies a pending request at once when one of these happens: the stop turns on, the agent is paused or revoked, or the call is cancelled. It removes the request files, so the request page reads as expired.
- **Session answers are kept apart.** "Allow until the agent disconnects" is stored in `session_grants`, apart from the user's `grants`. It used to overwrite them. `policy.effective_mode` reads it first, as `session-grant`. These replace it:
  - a grant the user sets;
  - a reset;
  - a new level.

  The bridge and the assistant's task drop their session's answers when they end.
- **AI Workspace windows.** In a window an agent drives, the Shell API refuses everything that loosens a setting or hides what was done (`workspace-change`): adding agents, levels, grants, sites, profiles, routes, resuming, lifting the stop, installing a client configuration, clearing the activity. Only the stop, pause and revoke work there.

**Changelog: this only tightens.** A capability the user set to "ask" goes back to "ask" when the session ends, not to the level's default. Nothing that was refused becomes allowed.

## Amendment 2026-11-03: the assistant's context, conversation, stream and entry points (UX5)

**Consent is per item and checked twice.**
- "Incluir esta página" reads the tab's visible text at once and keeps that copy in the browser, per window and in memory only. The panel gets sizes, never the text. A later Send sends that copy while the tab still shows the same address.
- The line above Send names the recipient (host and port, since another port can be another program), the model and the whole size of the request in code points, Nulavio's instructions included.
- The tools recompute the size and compare the recipient. They refuse with `size-changed` or `recipient-changed`, and then nothing is sent.
- A page is cut at 60 000 characters and a selection at 16 384, and the item says so before Send.

**A conversation per window (Q1, Q2, Q16, Q17, Q20).**
- It lives in `NulavioAI`'s memory only. It survives closing the side panel and is gone when the window closes or on "Começar conversa nova". The tools keep nothing (decision 4): each Ask carries its history.
- The page copy that went in a turn goes again to the same recipient, and the line says so. "Deixar a página de fora" stops that.
- When the provider changes, the conversation goes to the new recipient only after "Levar a conversa", and without the page.
- "Tentar de novo" says what it resends and sends exactly that.
- Above 200 000 characters, Send waits for a choice. Nothing is cut silently.

**Stream and stop.**
- With `"stream": true`, `nulavio ai assistant` writes NDJSON events on the same pipe, ending in exactly one terminal line. The contract is in [the architecture](../architecture/ai-bridge.md#assistant-stream-contract-ux5). It is not a new IPC: the same process per call, no socket and no permission.
- SIGTERM, or the end of stdin, cancels. A stop never cuts the AI Workspace's cleanup, and a call stopped mid-way is recorded as `cancelled`.
- The emergency stop, a pause or a revocation cuts a run at once (Q19).

**Answers.**
- Answers are a safe Markdown subset made with `h()` (no HTML, no image, no clickable link, nothing that loads).
- Sources are only passages quoted word for word from a page that went (Q13).

**Permission requests of the assistant's tasks (Q9).** A request shows once:
- as a card in the run's own side panel, with "Negar" first and focused, and the allow answers disarmed for a moment;
- or, when that panel is closed, as the request page in front in the run's window.

Never both, and never in an AI Workspace. The answer goes through the same `answer()`.

**Entry points (Q5–Q8).** None of them sends anything; each only puts something in the panel's next message and opens it, in the right window.
- **Selection menu:** "Perguntar ao assistente sobre a seleção". The text stays in the browser.
- **Shortcut:** Alt+Shift+A, a named command that never toggles the panel closed.
- **Omnibox keyword:** `@ia`. It only writes the question.
- **Quick action:** "Perguntar ao assistente sobre esta página" in the address bar.

None of them is offered in private windows or where an agent drives the browser.

**Manifest changes, with reasons.**
- `commands.open-assistant` is one more entry under an existing key, not a permission. It is the only way to get a shortcut that opens without closing.
- `omnibox.keyword` is a new key. The address bar is where most questions start, and the keyword takes text from it without a permission or an engine change. It is privileged like `commands`. The text never reaches search suggestions: the engine skips them for text that starts with "@" and names no engine (bug 1551049), and `test_search` 05b pins this with a positive control. No engine patch was needed.

**Visibility.**
- While the assistant's task acts, the band of its window says so and counts the steps, or says that it waits for the person. It offers "Parar tarefa" and "Pausar assistente".
- An agent connected through the bridge shows as "Agente conectado" in the user's windows. This comes from session markers that `nulavio ai serve` leaves while it runs (pid checked; files only, no process).

**Changelog.** These change what the assistant can do only in what the person sees and controls:
- Every new path either tightens (a refusal before sending, a stop, a pause) or puts text where the person sends it.
- The page copy that goes again in a conversation goes to the recipient that already received it, and the person can leave it out.

## Amendment 2026-11-24: an answer covers what its request showed, and profiles follow every call

**Change.**
- **Session answers have a site and a place.** A permission request names a site and where the agent acts (its AI Workspace or one of the user's profiles). "Allow until the agent disconnects" is kept for that pair (`session_grants[capability].scopes`) and `policy.effective_mode` counts it only for a call with the same pair. For `local_resources` the Bridge lets that host and port through in the engines of that place; the rest of this computer, the local network and `file:` still ask. The Shell's own check of an agent's local pages reads one file per Bridge, which lists the places answered in any of its engines. A request for a `file:` address names no path, so an answer for one covers every `file:` address in that place. For `submit_forms` the page's documents go on holding what they send. Without a pair, which is how the tool list and what an engine holds or lets through are decided, only the user's grant or level counts: an answer for `files` does not turn downloads on. An answer stored before this change counts for nothing. Settings says of a live answer that it is for the sites and places answered for. "Allow once" is for the call that asked; the same question is not asked twice in one call.
- **A profile the session has open follows every call.** At the start of each call the Bridge closes a profile that is no longer given to the agent, is given at another path, or whose `authenticated_sessions` is blocked, and every profile while another place is open and `multiple_profiles` is blocked. A call that acts on a tab of an open profile needs `authenticated_sessions` for the site the tab is at, a navigation there needs it for the site it goes to and for the site a redirect or the page took it to, and `multiple_profiles` is needed while another place is open; `tabs_list`, `downloads_list`, the result of an action that moved the tab, and the result of a navigation or new tab whose page went on to another site after those checks describe a profile only where acting there would not ask, the title included.
- **A site list also bounds addresses without a site** (point 7): `policy.host_of` gives `""` for every address that is not http(s), `file:` written with a host (which the engine ignores) and internal pages included, and no site list holds it. With no site list, `file:` stays what `local_resources` allows.
- **Hosts are read as the engine reads them.** `classify_url` refuses, before any lookup, a web address whose host has a character the engine never sends to its resolver (`net_IsValidDNSHost`: letters, digits and `.-$+_`) or an invalid IPv6 literal, and requests and logs show the host as the engine writes it (punycode, dotted IPv4, bracketed IPv6, no default port). A host with a character that UTS #46, which the engine follows, keeps and Python's IDNA 2003 codec maps to another (ß, ς, the zero-width joiners) is refused, since the two would not read it alike.
- **No routing out of an engine an agent drives.** In an engine started with `NULAVIO_AI_WORKSPACE`, in-page routing (ADR 0003, M5) does not watch the page's navigations, a typed or delivered link that a rule sends elsewhere stops at `routing/blocked.html` (`why=agent`), and `NulavioRouting.openIn`, `NulavioProfiles.switchTo` and `openTemporary` refuse (`agent-route`, `agent-window`). So do the engine's own ways of starting another profile of the group (the app menu's and the menu bar's Profiles lists, "Move tab to profile"), which go through the Shell's check in front of `SelectableProfileService.launchInstance` (`agent-window`; no unlock page either), and the chooser opened from such a window, which refuses before it reads a profile's state or asks for a secret, so it unlocks nothing (`browser/shell/chooser/chooser.mjs`, patch 0011). Two more start a profile through `Services.startup.createInstanceWithProfile`, which no check of the Shell's stands in front of: `about:profiles` ("Launch profile in new browser") and restoring a backup. At its start in such an engine, before it writes `GUARD_READY`, the Shell blocks `about:profiles` as the engine's `BlockAboutProfiles` policy does (in that engine only; a tab already at it is loaded again) and switches restoring off on the default branch, locked (`browser.backup.restore.enabled`; a person's own setting that already has it off is left as it is). An engine started from there would inherit the agent's environment.

**Changelog: this only tightens.** Every change answers fewer calls without asking, or opens fewer places. The person opens other profiles from one of their own windows, the engine's own profile menus, its chooser, `about:profiles` and restoring a backup included.

## Amendment 2026-11-25: capabilities no tool checks are not offered (#714)

No tool opens a private tab or shows network traffic, nothing asked before work in the background or before a headless engine, and a purchase or an account change is a click or a form, which `interact` and `submit_forms` govern; no tool tells one from any other (AI-T13).
