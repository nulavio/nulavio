# Threat model: profile unlock (Vault, phone, other methods)

Scope: encrypted Nulavio profiles and how they are unlocked ([ADR 0005](../adr/0005-phone-profile-unlock.md), [ADR 0006](../adr/0006-nulavio-vault.md), [architecture](../architecture/vault-and-unlock.md)). Assets: the profile DEK, the profile data, unlock secrets (password, recovery code, phone keys). Boundaries UB1–UB5 are defined in the architecture. Tests are in `tests/unit/test_vault.py` (S3, simulated phone, artificial data) unless noted; the Test column names the test class.

Nothing here protects an **unlocked** profile from malware running as the same user: it can read the mounted files and the storage key in memory. Nulavio never claims otherwise.

| U-T16 | Recovery code stolen | Paper or photo leaked | High entropy, shown once, replaceable: a new code, and the old code's envelope removed once the new code is typed back (#187). A replacement left unfinished (the program killed, the page left) is settled at the next unlock from locked: finished when that unlock used the new code, undone otherwise, and the unlock says which. An unlock that cannot save the key file then (a full disk) says it could not, and both codes keep working until one that can; one that cannot tell whether it saved (the file cannot be read back either) says that and points to the profile's unlock methods; one that saves but cannot record it inside the volume says that, as a change does. The command line confirms only the code it showed. While a replacement waits, the code being replaced cannot be removed, and the new code does not count as a way in for "the last method" | Thief with the code and a profile copy unlocks it. | U-T21 | Rollback of `vault.json` (restores a revoked phone's envelope or an old password) | Same-user malware or a restored backup while locked | `generation` in the metadata, mirrored inside the encrypted volume at every mount and at every change of the unlock methods, locked or not. For a change, a locked profile is mounted for that alone, at a private directory; the change does not happen if the volume cannot be mounted, and its record is written through a handle on the volume, so it lands there or is reported as not recorded. An older `vault.json` is refused at unlock and for a further change, and a volume whose generation could not be checked is unmounted again (detached, if a file in it is held open). One lock per profile covers the check and the write, and a change is refused when the key file is no longer the one it read, so two changes cannot both save "the next" generation; an unlock that was waiting meanwhile is told the key file changed, and opens when asked again | This is the launcher refusing the file, not the old secret losing its power: the volume is not re-encrypted, so the profile's files still open outside Nulavio with a key file kept from before the change and the secret that was valid then ([R70](residual-risks.md)). The record stops an older key file that was put back by itself (a restored backup, a synced folder). It is a file in the volume, and the volume vouches for each file's content, not for which version of a file is there: someone who also kept the volume's files from before the change can put the old record back with the old key file, or remove it, and Nulavio then opens the profile with the old secret. The key file is saved before the record is written: a process killed between the two, or a volume that goes away just then, leaves the change unrecorded until the profile is next unlocked from locked (unlocking a profile that is already open records nothing), and the old key file can be put back meanwhile (accepted, R70). The command line, the helper's answer and the browser's pages (unlock methods, phone) report the change with that warning, as a warning next to its result, and a new recovery code is still shown (#177). While a locked profile's methods are being changed, its files are readable and writable at `P.vault/maintenance-*` by the user's own processes (seconds; a system keyring that asks for its own password makes it longer); a change that was killed leaves that mount for up to about a minute, or until the profile is next used | Low | `ContainerTest.test_rolled_back_key_file_is_refused`, `HelperApiTest.test_a_method_changed_while_locked_is_recorded_in_the_volume`, `test_a_method_is_not_changed_when_the_volume_cannot_record_it`, `test_two_changes_from_the_same_key_file_do_not_both_go_through`, `test_the_record_goes_into_the_volume_or_nowhere`, `test_an_unlocked_profile_that_locks_during_a_change_gets_no_record_in_the_clear`, `test_a_change_that_was_saved_is_reported_even_when_its_record_failed`, `test_a_profile_whose_generation_cannot_be_checked_does_not_stay_open`, `test_one_change_at_a_time_and_nothing_left_mounted_by_a_killed_one`; `test_vault_ui` 18 |
