# Threat model: profile unlock (Vault, phone, other methods)

Scope: encrypted Nulavio profiles and how they are unlocked ([ADR 0005](../adr/0005-phone-profile-unlock.md), [ADR 0006](../adr/0006-nulavio-vault.md), [architecture](../architecture/vault-and-unlock.md)). Assets: the profile DEK, the profile data, unlock secrets (password, recovery code, phone keys). Boundaries UB1–UB5 are defined in the architecture. Tests are in `tests/unit/test_vault.py` (S3, simulated phone, artificial data) unless noted; the Test column names the test class.

Nothing here protects an **unlocked** profile from malware running as the same user: it can read the mounted files and the storage key in memory. Nulavio never claims otherwise.

| # | Scenario | Preconditions | Controls | Limits | Residual | Test |
|---|---|---|---|---|---|---|
| U-T1 | Offline theft of the profile (stolen disk, backup, synced folder) | Profile locked | Data encrypted; DEK only in envelopes; KEKs not on disk (password, phone) or outside the profile (keyring) | Weak password: offline guessing against Argon2id | Low (phone, strong password) / Medium (weak password) | `CopiedFilesTest`, `NoUnlockWithoutValidMethodTest` |
| U-T2 | Malware as the same user, profile **locked** | Infection while locked | Phone and password methods need the user; the keyring method does not (shown as `os_user_protected`) | Keylogger captures a password at next unlock; keyring readable | Medium | `KeyringTest`, `PhoneReleasesKeyTest` |
| U-T3 | Malware as the same user, profile **unlocked** | Session open | Lock when idle (auto-lock), short sessions for sensitive profiles | Full read access to mounted data and keys in memory | **High; out of reach** | documented (TB6) |
| U-T4 | Malware with root/administrator | — | None at the browser level | Everything | Out of scope | — |
| U-T5 | Compromised local IPC (fake coordinator, injected messages) | Same-user malware | Phone requests are signed by the paired desktop key; responses are bound to a one-time session key | Same-user malware can steal the desktop identity (0600 file) and send requests; the user still has to approve on the phone | Medium | `UnpairedDeviceTest` |
| U-T6 | Fraudulent pairing | Attacker on the network | QR carries a pairing secret; only a reader of the QR can say hello; 6-digit comparison on both screens | A user who skips the comparison | Low | `SubstitutedPairingTest` (hello without the secret) |
| U-T7 | Substituted QR code (screen tampering, shoulder relay) | Attacker controls what the phone scans | Codes differ on the two screens; desktop key in the QR must sign the accept message | User does not compare | Low/Medium | `SubstitutedPairingTest` (swapped keys, copied QR raced) |
| U-T8 | Replay of an unlock response | Network observer or same-user malware | One-time session key and request id; desktop accepts once | — | Low | `ReplayTest` |
| U-T9 | Fake desktop asks the phone for approval | Attacker with a stolen desktop identity or none | Unpaired desktops are rejected; requests show profile and desktop names; phone UI says "only approve if you just asked" | Paired-identity theft (U-T5) plus a user who approves | Medium | `UnpairedDeviceTest` |
| U-T10 | User tricked into approving | Social engineering | Context on the phone; requests expire in 60 s; nothing to approve unless the desktop asked | Human factor | Medium | `ExpiredChallengeTest` |
| U-T11 | Compromised phone | Malware on the phone | Phone keys under a hardware key with per-use biometrics; revoke the phone from the desktop | Rooted phone can capture keys after an approval (v1: key briefly in app memory) | Medium | `UnpairedDeviceTest` (revoked), `SecondPhoneTest` |
| U-T12 | Compromised Companion build | Supply chain | Reproducible F-Droid build; signature pinning; minimal permissions | Store or signing-key compromise | Medium | (S11) |
| U-T13 | Key material in memory | Same-user malware or crash dump | Short-lived buffers wiped (`sodium_memzero`); no core dumps of the coordinator | Python copies; storage key lives while unlocked | Medium | — |
| U-T14 | Data exposed by extensions | Malicious extension in the profile | Engine permission model; Guard extension audit | Extensions see what the profile sees when unlocked | Medium | — |
| U-T15 | Secrets in logs | Developer mistake | Logs never contain secrets; tests scan outputs and files | — | Low | `NoSecretsInLogsTest` |
| U-T16 | Recovery code stolen | Paper or photo leaked | High entropy, shown once, replaceable (new code, old envelope removed) | Thief with the code and a profile copy unlocks it | Medium | `RecoveryCodeTest` |
| U-T17 | Lost device | Phone lost | Remove phone (envelope deleted), other methods remain; key rotation offered | Profile copies taken before removal stay decryptable with that phone | Low/Medium | `UnpairedDeviceTest` (revoked), `SecondPhoneTest` |
| U-T18 | Downgrade to a weaker method | Attacker edits metadata or blocks the phone | Combined policies are cryptographic (one envelope needs both KEKs); metadata MAC detects edits; no automatic fallback | Deleting envelopes is a denial of service, not a downgrade | Low | `TamperTest`, `CombinedPolicyTest` |
| U-T19 | User or profile switched during an operation | Concurrent actions | Requests bound to profile id and envelope id; one pending request per profile | — | Low | `ReplayTest` (old response, new request) |
| U-T20 | Unlock after expiry | Delayed response | Expiry checked on both sides | Clock skew ±120 s | Low | `ExpiredChallengeTest` |
| U-T21 | Rollback of `vault.json` (restores a revoked phone's envelope or an old password) | Same-user malware or a restored backup while locked | `generation` in the metadata, mirrored inside the encrypted volume at every mount; an older `vault.json` is refused | A rollback made while the volume was never mounted again cannot be compared (no newer mirror) | Low | `ContainerTest.test_rolled_back_key_file_is_refused` |
| U-T22 | Crash or kill while unlocked | Power loss, OOM, SIGKILL | DEK only in memory; atomic writes; temporary file holds only envelopes; backup fallback | Swap or hibernation images may hold memory pages (mitigate with encrypted swap) | Low | `CrashTest` |
| U-T23 | Plaintext written into a locked profile (engine started directly, another program) | Profile locked | Mount point empty and read-only (0500) while locked; a non-empty mount point is refused at unlock | The instant of mounting (mode 0700 for fusermount) | Low | `test_vault_profiles` (direct engine start), `test_plaintext_in_a_locked_profile_blocks_unlock` |
| U-T24 | Volume left open after a crash | Launcher killed | Engine keeps working; `nulavio vault status` reports an open volume with no engine; `lock` refuses while an engine runs (no data loss) | Stays open until the user locks it (or an idle timer, when configured) | Medium | `SupervisedRunTest` (crash, SIGTERM) |
| U-T25 | Plaintext left behind when encrypting an existing profile | Profile was used before encryption | Originals deleted after a verified copy; the command warns | SSDs, snapshots and backups can keep fragments | Medium | `test_encrypt_existing_profile` |
| U-T26 | Wrong volume for a key file (swapped directories) | Same-user tampering | gocryptfs rejects another key; the state file binds profile id | — | Low | `test_wrong_key_and_wrong_container` |
| U-T27 | Password or recovery code typed in the browser | Same-user malware reading browser memory; a malicious extension | Typed only into the Shell's own page (extension pages are not reachable by websites or other extensions); sent to the Vault helper on stdin, never argv or disk; never logged | JavaScript strings cannot be wiped; a keylogger or memory reader running as the user sees it (U-T2) | Medium | `test_vault_ui`, `HelperApiTest.test_secrets_never_reach_argv_or_logs` |
| U-T28 | Profile left unlocked after its window closes | Browser-group profile unlocked from another profile | Watcher locks after the instance exits (lazy detach after a minute if helpers still hold files) or after two minutes unused | A watcher killed with the session leaves it open (`nulavio vault status` shows it) | Low/Medium | `test_vault_ui` test 2, `HelperApiTest.test_autolock_*` |
| U-T29 | Someone on the local network answers for the phone (announces the same mDNS name, connects first) | Attacker on the same network | Everything the desktop accepts is authenticated by nv1; an unsigned or wrongly signed answer is ignored and the desktop keeps resolving until the request expires (`test_phone_link` 04, `test_companion_protocol`) | Delay or denial of the phone method on that network | Other methods stay offered |
| U-T30 | The phone's debug build is installed by mistake | Developer build on a user's phone | The test hooks (code by intent, port in the log) exist only in debug builds; F-Droid builds release (`test_companion_build`) | A debug build accepts a code without the camera; it still needs the user's authentication | Install only release builds |
