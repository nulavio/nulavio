# Hardening

What Nulavio applies today, how each item is verified (the Track A preview it was first written for is no longer offered, #464), and which host-level options were evaluated. Nothing here disables or relaxes an upstream protection.

Defaults that cannot be read at a start leave the record's as they were, and a change is reported against them at the next start that reads them. A `user.js` finding and a native-messaging, PKCS#11 or managed-storage manifest have no undo: the card offers "Show file" and "Keep", and the person edits or deletes the file (a setting that `user.js` changed can be put back from its own card, until `user.js` writes it again at the next start). An extension removed and a change of the managed policies offer only "Understood". Changes made in the browser during a session are followed, never reported, and so is an update the engine downloaded and held for the next start (the record notes the version to expect and the digest of the file the engine holds; only that version, installed from that very file, with the extension neither turned on nor off meanwhile, passes; when either digest cannot be read, it is reported). A record written before this has no such set: the first start after the update to a build with it still reports the set once if that update also changed the build's default, and so does a start after one that changed it but ended before the Guard saved its record. The record keeps the SHA-256 of each extension's package, read whole from the file at every look whatever its size, and a difference in it is reported like a difference in version (#136): the engine says nothing of another file under the same version, and in the runs made for #136 it went on reporting the old version of a file replaced while it ran. ## Deliberately **not** changed

| Upstream protection | Why it stays |
|---|---|
| Safe Browsing (phishing, malware, downloads) | Removing it weakens anti-phishing. A privacy-preserving replacement must be proposed and evaluated first (ADR candidate) |
| Remote Settings (OneCRL, CRLite, add-on blocklist) | Certificate revocation and malicious-extension blocking depend on it |
| Extension auto-updates | Security fixes for extensions |
| Engine updates | Delivered by Nulavio's signed packages under the [update policy](../architecture/update-policy.md) |
| DNS | Track A: Fedora disables DoH (`network.trr.mode=5`) to respect the system resolver, and Nulavio keeps that. Track B (S15): the new tab asks once how to look up sites: the computer's resolver (mode 5, "off by choice", which also keeps Mozilla's regional roll-out off), encrypted DNS with fallback (mode 2) or encrypted only (mode 3), through Cloudflare (the engine's default, [Mozilla's resolver program](https://wiki.mozilla.org/Security/DOH-resolver-policy)), [Quad9](https://quad9.net/doh-quad9-dns-servers/), [Mullvad](https://mullvad.net/en/help/dns-over-https-and-dns-over-tls) or an https:// address of the user's. Until the user answers, the engine's default applies. Nulavio runs no resolver; the UI says the chosen resolver sees the lookups. Even "encrypted only" leaves some names to the computer's resolver: local names (`localhost`, `.local`), names in the hosts file, names a setting or a policy excludes, and the resolver's own name ([R40](residual-risks.md)); the option says so, and Settings lists the excluded names while lookups are encrypted. `test_dns` proves lookups reach the chosen resolver and that "encrypted only" fails closed |
| `privacy.resistFingerprinting` | It fixes window sizes and breaks many sites, with no way out per site. The engine's fingerprinting protection for the Strict category is used instead, with Nulavio's additions ([measured](../research/fingerprinting.md)); of what RFP does, the UTC time zone is one of them since ADR 0017, with a switch per site. RFP may become an opt-in "hardened" mode |

## Host-level options evaluated

| Option | Benefit | Blockers found | Status |
|---|---|---|---|
| **Flatpak** | Filesystem confinement and portals | Native messaging: the host-side proxy (`xdg-native-messaging-proxy`) now ships in Fedora 44 and Ubuntu 26.04+, so it is solvable; a second packaging and update path for no gain over bubblewrap | **Not now** ([spikes](phase5-spikes.md#flatpak-and-native-messaging)) |
| **bubblewrap wrapper** | Hide `~` except the profile and Downloads from the browser process | Measured: the engine's sandbox is unchanged inside it on Fedora; on Ubuntu its content processes would lose their own namespaces, so the launcher checks that before a confined start and refuses ([#282](https://github.com/nulavio/nulavio/issues/282)); uploads only from Downloads; no session bus inside (no portals, notifications or media keys); no host device nodes but the GPU and cameras (no security keys or gamepads); a session with X11 only is refused | **Adopted as opt-in** `nulavio run --confined` ([spikes](phase5-spikes.md#bubblewrap)), from a source checkout only; **not part of 1.0**, since a package install cannot start it (#283, #466) |
| **SELinux policy module** | Mandatory access control for the browser domain on Fedora | Needs root on every machine and per-release maintenance; the browser runs `unconfined_t` like Fedora's Firefox; bubblewrap covers the filesystem part without root (from a source checkout; not part of 1.0, #466) | **Not adopted** ([spikes](phase5-spikes.md#selinux)) |
| **Secret Service / KWallet for engine logins** | OS keyring storage | Gecko on Linux does not use it for `logins.json`. The spec does not enforce per-application access: any same-user process can usually read an unlocked collection | Not a security gain against T-LOCAL; see [password providers](../architecture/password-providers.md) |

## User recommendations (shown in docs and onboarding)

1. Prefer an external manager that locks (KeePassXC, Proton Pass, Bitwarden) over engine-stored passwords. If you keep engine passwords, set a **Primary Password**.
2. Keep the system updated (`dnf upgrade` or `apt upgrade`): Nulavio's security releases come from its repository. The Flatpak bundle that came with 160.0-0.4 to 0.6 has no update channel (R75): move to the package.
3. Review extensions with "access your data for all websites" next to a password manager.
4. Use a separate Nulavio profile for work (flow G).

## Guard at run time: what it catches and how it can be bypassed

Phase 5 asks for a bypass analysis of each control. Guard is **detection**: it tells the user what changed outside the browser since the last run, so persistence left by tools and generic malware does not go unnoticed. It does not stop a program running as the user from reading cookies or passwords ([threat model S11](threat-model.md#s11--local-malicious-process-as-the-same-user-infostealer)).

| Check | Typical abuse it surfaces | Bypass | Residual |
|---|---|---|---|
| Extensions (added, replaced, turned on, removed) | A malicious extension dropped into the profile, or a disabled one turned on by editing `extensions.json` | Edit Guard's record (`nulavio-guard.json`) too; install through a policy (reported as a policy change instead); change an extension's file at the moment the browser itself installs, updates or switches that same extension, at a start or while it runs (what the browser announces is followed, the file's digest included); write the version and the file's digest to expect into the record's `expected` field (the same file as the record itself, so no new reach); replace the file the engine holds for the next start while the browser still runs, before Guard last notes its digest, which is at shutdown (the engine still refuses, at install, a file Mozilla did not sign for that extension) | Nulavio-aware malware can hide; the engine's own sideload prompt still applies to dropped XPIs; a replaced file is noticed by the SHA-256 of the package (since #136), whatever version the engine reports: another file with the same version, a file changed in any byte, and a file renamed into place while the browser runs, which is reported at the Guard's next look (a look is brought about by a change in the browser or by closing it, so at the latest it waits in the bar of the next start; the engine itself keeps running the file it had open until then). A record written before #136 has no digest: the first look after the update takes it, and a file replaced with the same version between the last start of the old build and the first of the new one is not seen. An extension turned off from outside is not reported (one turned on is). An unpacked extension (a folder, not a package) has no digest and is still noticed by its version only |
| Settings that protect or route traffic (proxy, DNS over HTTPS, TLS, sandbox, signatures, Safe Browsing, HTTPS-Only, tracking protection, home page, remote debugging) | A proxy for interception, Safe Browsing turned off, remote debugging enabled to dump cookies | Edit the record; change a setting not on the list | The list is short on purpose; `guard-rules.json` prefs are all on it (unit test) |
| Certificate authorities in the profile's store | A root added for TLS interception (`certutil -A`) | Edit the record; add the root to the system store instead (needs root) or through a new security module (reported as such) | System trust stores are outside the profile |
| Security modules (PKCS#11) | A module loaded into the browser process | Edit the record | — |
| Native-messaging, PKCS#11 and managed-storage manifests, and the program each starts (digest) | A fake password-manager host, a swapped host binary | Edit the record; replace a host binary larger than 64 MB (checked by size and time only) | Hosts in system directories need root to change |
| Managed policies | `ExtensionSettings` force-installing an extension, settings locked by policy | Edit the record; change policies in the same update as Nulavio itself (a new build's policies are not reported) | The policies file of a user-owned install is user-writable; packaged installs are root-owned (S18) |
| `user.js` | Preferences forced at every start | Edit the record | Undoing a setting that `user.js` forces lasts until the next start; the page says to edit the file |
| Default search engines | Search hijacking | Edit the record | — |

**Limits shared by every check.** The record lives in the profile (encrypted at rest for protected profiles, and unreadable while locked), so any program running as the user while the profile is unlocked can rewrite it; Guard reports at the next start, not the moment a file changes (extension files are the exception: they are also looked at during the session, when the engine says it found something on disk, when a watched setting or an extension changes in the browser, and at shutdown); certificate authorities and modules added through the browser's own certificate manager are reported at the next start as well (one "Keep"); Track A has no Shell, so this check exists only in the Nulavio build; temporary profiles and profiles an agent is driving are not checked. Changes to the installed browser itself (`omni.ja`, `libxul.so`) are out of reach of a check that runs inside it: packaged, root-owned installs are the answer (S18). See [R38](residual-risks.md).
